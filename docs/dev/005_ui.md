# 005 UI

## Purpose

Define what the UI layer owns in ani2arr.

This document should be read together with:

* `001_architecture.md`
* `002_structure.md`
* `011_ai_guardrails.md`

---

## Core rule

The UI layer owns user-facing features and reusable components.

It includes:

* feature UIs
* reusable UI primitives and composites
* feature-local hooks
* feature-local view state

It does not own infrastructure or domain rules.

---

## UI boundaries

UI must stay separated from infrastructure.

UI should go through the app boundary.
It should not depend directly on:

* raw storage access
* raw provider API access
* background orchestration
* domain resolution logic

Allowed dependency direction:

* `features -> components + rpc + shared/config + small shared/types`
* `components -> shared/config + small shared/types`

Disallowed:

* `features -> storage`
* `features -> integrations`
* `components -> storage`
* `components -> integrations`
* `components -> runtime`

---

## `features/` vs `components/`

Use `features/` for product UI that only makes sense inside a specific feature.

Put in `features/`:

* feature-local UI
* feature-local hooks
* feature-local state
* feature-local helper functions

Use `components/` for reusable UI.

Put in `components/`:

* reusable primitives
* reusable composites used by multiple features
* generic layout wrappers

Rule:
If a component is tightly coupled to one feature, keep it in that feature.
Do not move something into `components/` just because it is visually small.

---

## Hooks

Hooks follow ownership.

Use feature-local hooks inside the feature.
Do not put feature-specific hooks into shared support folders.

Create a custom hook only when it improves clarity.
Do not extract a one-off hook just to move code out of sight.

---

## Forms and styling

Use the repo’s standard UI conventions:

* use `react-hook-form` for forms
* keep form state aligned with schemas
* use Tailwind consistently
* use the canonical `cn` helper from `src/shared/utils/cn.ts` for class composition whenever conditional or merged class names are needed

Do not introduce:

* ad hoc form state systems without strong reason
* duplicate class-name helpers
* new visual abstraction layers without a clear repeated need

---

## Browse-card `enabled` vs `visibility`

For browse cards, `enabled` controls shell existence.

If a provider is not enabled for a browse surface, the shell and its injected browse-card DOM must not exist.

`visibility` is a UI presentation choice for an enabled browse shell only.
It is limited to:

* `always`
* `hover`

`visibility` must not be used as a disable mechanism.
It does not apply to anime-page shells.

Runtime owns shell eligibility and teardown.
UI owns how an enabled browse-card shell is presented and rendered.

---

## UI splitting rules

Split UI by responsibility, not by line count.

Keep a component together when:

* it has one clear responsibility
* splitting would only move JSX around
* local state and rendering are tightly connected
* subparts are not reused

Split when:

* subparts have their own state
* subparts are reused elsewhere
* visual sections have clearly different responsibilities
* the parent becomes hard to read because unrelated concerns are mixed

Do not over-split the UI into many tiny files with indirection.

---

## UI-specific anti-patterns

Avoid:

* putting raw integrations into UI code
* putting runtime mechanics into UI code
* putting domain logic into reusable components
* moving feature code into shared support folders
* abstracting UI for symmetry alone

---

## Decision checklist

Before placing UI code, ask:

1. Is this feature-local or truly reusable?
2. Does it belong in `features/` or `components/`?
3. Is it depending on RPC rather than raw infrastructure?
4. Would splitting it improve ownership and navigation?

If ownership is clear, keep the UI code with that owner.

---

## Stable conclusion

The UI layer owns user-facing behavior, not infrastructure.

Use:

* `features/` for feature-local UI
* `components/` for reusable UI
* feature-local hooks where possible
* minimal, meaningful UI splits

Keep UI separated from storage, integrations, runtime mechanics, and domain implementation details.
