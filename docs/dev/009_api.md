# 009 API

## Purpose

Define what the external API layer owns in ani2arr.

In the planned architecture, this layer lives in `integrations/`.
This document should be read together with:

* `001_architecture.md`
* `002_structure.md`
* `007_core.md`
* `011_ai_guardrails.md`

---

## Core rule

The API layer owns raw external integrations.

It includes:

* AniList transport
* Sonarr transport
* Radarr transport
* endpoint helpers
* DTO normalization
* provider API contract details

Rule:
If it talks to an external system and is mainly about that system’s contract, it belongs here.

If it mainly owns app decisions, it belongs in `core/`.
If it mainly owns browser messaging or startup mechanics, it belongs in `runtime/`.

---

## Planned folder ownership

The target owner is `integrations/`, not a vague catch-all API bucket.

Typical subfolders:

* `integrations/anilist/`
* `integrations/sonarr/`
* `integrations/radarr/`
* `integrations/shared/` only if truly needed

Use `integrations/shared/` sparingly.
Only put code there when it is truly shared transport infrastructure.

---

## What belongs here

Put these in `integrations/`:

* HTTP request code
* endpoint helpers
* external DTOs
* DTO normalization
* integration-specific request helpers
* shared Arr transport code if there is a real shared owner

Keep transport-local DTOs near the transport boundary.

---

## What does not belong here

Do not put these in `integrations/`:

* mapping policy
* library policy
* AniList-derived app state
* app decisions
* UI logic
* runtime messaging
* alarms
* typed RPC contract code

Integrations are not app services.
They are raw external system code.

---

## API vs core

Keep these separate:

* `integrations/` = raw external system contracts and transport
* `core/` = domain workflows and app decisions

Core may depend on integrations.
Integrations must not absorb mapping rules, library rules, or other business policy.

---

## API vs RPC and runtime

Keep these separate:

* `rpc/` = typed cross-context app boundary
* `runtime/` = browser/WXT mechanics
* `integrations/` = raw external systems

Do not put proxy transport, broadcasts, alarms, or startup wiring into integrations.
Do not make integrations the RPC boundary.

---

## Dependency rules

`integrations/` may depend on:

* `shared/utils`
* `shared/types`
* integration-local helpers

Disallowed:

* `integrations -> ui`

If a file has a stronger owner in `core/`, `rpc/`, `runtime/`, or `storage/`, keep it there.

---

## Type ownership

Keep transport DTOs near the transport boundary.

Rules:

* integration DTOs belong in `integrations/...` when they are transport-local or endpoint-specific
* transport-local raw request and response shapes should prefer a `*Dto` suffix
* do not use GraphQL-specific names like `*Node` as the default repo convention for transport payloads
* a transport DTO may intentionally differ from a domain type
* do not move transport-local types into `shared/types` without a real cross-cutting need
* do not duplicate the same transport shape across multiple owners
* do not redefine every nested leaf shape in `integrations/` if an identical canonical type already exists elsewhere

Keep transport wrappers and endpoint-specific payloads local to integrations.
Reuse an existing canonical nested shape when the structure and meaning are the same.

Pragmatic rule:

* if a type shape and meaning are reused unchanged across two or more domains, one canonical type in `shared/types/` is preferred over duplicate owner-local copies
* if an endpoint has a narrower or different transport shape, keep that integration-local and use a `*Dto` suffix when helpful
* a full provider resource reused unchanged across integrations, library flows, and RPC may live in `shared/types/`, but a lookup candidate or endpoint-local wrapper should stay with the transport owner

Example:

* a response page wrapper for AniList search belongs in `integrations/anilist`
* an identical title or image leaf type should not be redefined in `integrations/anilist` just to mark it as transport-local

---

## Naming rules

Use literal integration names:

* `anilist`
* `sonarr`
* `radarr`

When talking about Sonarr and Radarr together, use `providers`.

Avoid vague names like:

* `manager`
* `helper`
* `common`
* `misc`

---

## API-specific anti-patterns

Avoid:

* putting app policy into integrations
* putting runtime orchestration into integrations
* putting UI behavior into integrations
* creating shared transport abstractions just for symmetry
* spreading one external contract across multiple unclear owners

---

## Decision checklist

Before placing code in `integrations/`, ask:

1. Is this mainly about an external system contract?
2. Is it transport code, a DTO, or an endpoint helper?
3. Is it not better owned by `core/`, `rpc/`, `runtime/`, or `storage/`?
4. Does placing it here keep app policy out of the integration layer?

If yes, it likely belongs in `integrations/`.

---

## Stable conclusion

The API layer is the raw external integration layer.

It owns:

* AniList transport
* Sonarr transport
* Radarr transport
* endpoint helpers
* DTO normalization
* provider API contract details

It does not own:

* app rules
* UI
* RPC contracts
* runtime mechanics
