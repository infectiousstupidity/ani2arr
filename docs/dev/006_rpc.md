# 006 RPC

## Purpose

Define what `rpc/` owns in ani2arr.

## Core rule

`rpc/` is the typed boundary between UI and background work.

It owns:
- the app API contract
- RPC schemas
- RPC handlers
- handler dependency types

It does not own:
- startup wiring
- alarms or broadcasts
- raw provider transport
- reusable business workflows

## Handler rule

Handlers are boundary adapters.

Handlers may:
- validate input and output shape
- ensure required configuration
- call the correct core workflow
- translate boundary errors
- trigger boundary-side refresh or invalidation

Handlers must not:
- become the owner of business rules
- absorb raw provider client behavior
- own browser lifecycle logic
- call other RPC handlers

If logic is shared between handlers, move it into `core/`.

## Organization rule

Organize `rpc/handlers/` by app capability, not by vendor.

Good examples:
- `library.handlers.ts`
- `provider.handlers.ts`
- `options.handlers.ts`
- `mapping.handlers.ts`

Use provider-specific method names inside those files when the RPC action itself is provider-specific, such as `addToSonarr` or `updateRadarrMovie`.

Do not split one operation into a separate handler file unless that file is itself the clear public boundary module.

## Dependencies

`rpc/` may depend on:
- `core/`
- `shared/config`
- `shared/types`

`runtime/` may depend on `rpc/` for transport registration and service exposure.

Handler dependencies should be services, clients, stores, or core workflows.
They should not be other handlers.

## Schemas and types

- Keep RPC schemas near RPC.
- Use Valibot for real runtime boundaries.
- Prefer deriving types from schemas when the schema is canonical.
- Reuse an existing canonical shared type when the meaning is unchanged.
- Do not create RPC-local clones of a type just because it crosses the boundary.

## Anti-patterns

Avoid:
- ad hoc message sprawl instead of typed RPC methods
- mixing startup wiring with handlers
- putting raw provider API details into handlers
- duplicating the same workflow across handlers
- handler-to-handler indirection

## Stable conclusion

`rpc/` should be easy to read:
- one obvious public boundary
- thin handlers
- real workflows in `core/`
- transport details in `integrations/`
