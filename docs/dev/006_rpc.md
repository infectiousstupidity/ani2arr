# 006 RPC

## Purpose

Define what `rpc/` owns in ani2arr.

This document should be read together with:

* `001_architecture.md`
* `002_structure.md`
* `004_runtime.md`
* `011_ai_guardrails.md`

---

## Core rule

`rpc/` owns the typed application boundary between UI and background/domain work.

If a module mainly defines:

* the app API contract
* input/output schemas
* request handler boundaries
* handler dependency types

then it belongs in `rpc/`.

If it mainly owns browser messaging transport, broadcasts, alarms, or startup, it belongs in `runtime/`.
If it mainly owns business rules, it belongs in `core/`.

---

## What `rpc/` owns

Put these in `rpc/`:

* RPC contract
* RPC schemas
* RPC handlers
* handler dependency types

Typical subfolders:

* `rpc/handlers/`

Rule:
RPC defines what the app exposes across contexts.
It does not own runtime bootstrapping.

---

## What `rpc/` does not own

Do not put these in `rpc/`:

* browser startup wiring
* alarms
* broadcasts
* tab broadcast orchestration
* proxy transport setup
* raw provider clients
* raw provider integration details
* domain implementation details that belong in `core/`

---

## RPC vs runtime messaging

Keep these separate:

* RPC = typed request/response app actions
* runtime messaging = lifecycle signals, broadcasts, permissions, alarms, and transport wiring

Use RPC when the UI or another context needs a typed app operation.
Use runtime messaging when the app needs fan-out or browser-level coordination.

Do not let ad hoc messages replace typed RPC methods.
Do not move transport concerns into RPC handlers.

---

## RPC vs handlers vs core

Handlers are boundary adapters.

Handlers should:

* validate input and output shape
* call the correct domain owner
* translate boundary errors when needed

Handlers should not:

* become the canonical owner of business rules
* absorb browser lifecycle logic
* absorb raw transport client logic

Rule:
If logic is reusable as an app rule, it likely belongs in `core/`, not in a handler.

---

## Schemas and types

Keep RPC schemas near RPC.

Rules:

* use Valibot where applicable
* prefer deriving types from schemas when the schema is canonical
* keep RPC payload and schema-derived types in `rpc/`
* do not hand-maintain duplicate schema-shaped types if the schema can derive them
* if a canonical shared type already exists and the RPC meaning is the same, reuse it instead of cloning it into `rpc/`

Use Valibot for RPC because RPC is a runtime boundary.
The handler receives unknown input and returns a contract that should stay explicit.

Do not use a Valibot schema for an internal helper type unless that helper is itself a validated boundary.

RPC payloads may intentionally differ from internal domain types.
That is acceptable when the boundary is real and explicit.

Do not create RPC-local copies of a type just because it crosses the RPC boundary from another domain.
Only define a separate RPC type when the RPC contract shape or meaning is actually different from the canonical shared type.

---

## Dependency rules

`rpc/` may depend on:

* `core/`
* `shared/config`
* `shared/types`

`runtime/` may depend on `rpc/` for transport registration and service exposure.

Avoid the reverse direction where it weakens ownership.

In particular:

* UI should call RPC, not raw core internals across contexts
* RPC should not own runtime bootstrapping
* integrations should not become the RPC boundary

---

## Naming rules

Use literal RPC names.

Prefer:

* `schemas.ts` or `*.schema.ts`
* `handlers.ts` or `*.handlers.ts`
* direct method names that describe the app action

Avoid vague names that hide the boundary role.

---

## RPC-specific anti-patterns

Avoid:

* ad hoc message sprawl instead of typed RPC methods
* putting alarms or broadcasts into `rpc/`
* mixing proxy transport setup with handler logic
* putting raw provider API details into handlers
* duplicating domain logic across multiple handlers
* duplicating schema-shaped types by hand

---

## Decision checklist

Before placing code in `rpc/`, ask:

1. Is this defining the typed cross-context app API?
2. Is this a schema, handler, or handler-boundary type?
3. Is it not better owned by `runtime/`, `core/`, or `integrations/`?
4. Does it keep transport concerns separate from app contract concerns?

If yes, it likely belongs in `rpc/`.

---

## Stable conclusion

`rpc/` is the typed app boundary.

It owns:

* contracts
* schemas
* handlers
* boundary types

It does not own:

* browser transport wiring
* broadcasts
* alarms
* raw integrations
* domain business rules
